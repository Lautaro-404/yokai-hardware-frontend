Arquitectura del sistema

Cómo está armada la tienda online de hardware y tecnología: qué piezas la componen, cómo se comunican y por dónde pasa una compra, desde que el cliente inicia sesión hasta que el administrador despacha el pedido.

Vista general

Es una aplicación web en capas. El navegador habla con el frontend, el frontend consume una API REST hecha en Java y la API guarda todo en una base de datos relacional. Cada capa solo se comunica con la inmediata siguiente.

Componente obligatorioComponente opcional (extra del plan)

El backend en Java está decidido por votación, la base de datos es PostgreSQL y el frontend es React. El hosting es una propuesta que el grupo todavía tiene que confirmar.

Qué hace cada capa

Frontend

Muestra el catálogo, el carrito, el checkout y el panel de administración con la temática yokai. Es responsive y solo se comunica con la API.

Seguridad

Un filtro valida el token JWT de cada pedido. Las contraseñas se guardan con BCrypt y las rutas de administración exigen el rol ADMIN.

Controller

Recibe las peticiones, valida los datos de entrada y responde con DTOs. No contiene lógica de negocio.

Service

Aplica las reglas del negocio: control de stock, armado de pedidos y cálculo de totales. Maneja las transacciones.

Repository

Lee y escribe en la base de datos con Spring Data JPA, usando las entidades del paquete model.

Base de datos

Guarda usuarios, productos, categorías, marcas y pedidos. Es la única fuente de verdad del stock.

Recorrido de una compra

Así viaja una compra por el sistema. Las rutas son de ejemplo: el contrato final de la API se define en la fase de diseño.

  1. Inicio de sesión. El cliente envía sus credenciales a POST /api/auth/login y recibe un token JWT que el frontend manda en cada pedido siguiente.
  2. Catálogo. GET /api/productos con filtros de marca, precio, categoría y disponibilidad, paginado.
  3. Carrito. El cliente agrega, quita o cambia cantidades con POST /api/carrito/items.
  4. Checkout. POST /api/pedidos con los datos de envío. El servicio valida el stock, crea el Pedido y sus DetallePedido y descuenta el stock en una sola transacción; si algo falla, se revierte todo.
  5. Seguimiento. El cliente ve su historial con GET /api/pedidos/mis-pedidos.
  6. Despacho. El administrador cambia el estado con PATCH /api/admin/pedidos/{id}/estado.

El estado visible del stock (“En stock”, “Últimas unidades”, “Sin stock”) no se guarda: se calcula a partir del stock y del stock mínimo. Si se implementa la reserva temporal durante el pago, se suma la entidad ReservaStock.

Seguridad y roles

Hay dos roles. El cliente explora, compra y ve solo sus propios carritos y pedidos. El administrador gestiona productos, categorías, stock y estados de pedidos. Las entradas se validan en el controlador y los errores se devuelven con un formato uniforme. Las credenciales viven en variables de entorno y nunca en el repositorio.

Despliegue

El backend y la base de datos gestionada se publican en un servicio como Render, Railway o Fly.io, con variables de entorno para la conexión y las claves. El frontend en React se publica por separado, en Vercel o Netlify, y apunta a la URL pública de la API. El primer despliegue se hace en la primera semana para detectar problemas de hosting a tiempo.

Decisiones pendientes

Extras: cuál de los diferenciales (armador de PC, filtros por caso de uso, reserva de stock) se suma una vez que el MVP esté desplegado.
